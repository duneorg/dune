# Skill: Dune Auth

Public (non-admin) user authentication. Two modes — pick one in `site.yaml`. Both populate `ctx.state.siteUser` (**not** `ctx.state.user`) with the same shape; middleware works identically regardless of mode.

**As of this writing, this entire system is unreachable from outside `@dune/core`.** `mountDuneAuth()` (`src/auth/mount.ts`) is fully implemented but has **no public export path** — it isn't listed under any `@dune/core/*` subpath in `deno.json`, and the root `@dune/core` doesn't re-export it either (`grep -n "mountDuneAuth" deno.json src/mod.ts` turns up nothing). `dune serve` and the generated `main.ts` entrypoint template never call it automatically. So `auth:` config in `site.yaml` currently has **no effect at all** — `ctx.state.siteUser` stays `null` forever and none of the `/auth/*` routes below exist, no matter how it's configured. Everything below documents the real implementation; none of it is currently wireable into a site without editing `@dune/core` itself or waiting for the export to be added.

---

## Mode 1: `dune` — built-in session stack

Dune owns the session lifecycle. Credential verification is delegated to OAuth providers or magic link. **No passwords, and no admin-provisioned local users** — see Gotchas.

### Minimal config (OAuth only, no server-side user store)

```yaml
# site.yaml
auth:
  mode: dune               # default — can be omitted
  userStore: session        # identity embedded in the session record — no data/site-users/ files
  sessionLifetime: 604800   # seconds (7 days) — flat field, default 2592000 (30 days)
  providers:
    github:
      clientId: "${GITHUB_CLIENT_ID}"
      clientSecret: "${GITHUB_CLIENT_SECRET}"
```

**There is no `session.secret`/`SESSION_SECRET` config anywhere in the real auth system.** Sessions are opaque server-tracked IDs stored under `{admin.runtimeDir}/site-sessions/`, not signed/encrypted cookies — nothing reads a signing secret. See Gotchas.

### With persistent user records + magic link

```yaml
auth:
  mode: dune
  userStore: local          # JSON files at data/site-users/ + by-email/ index
  providers:
    github:
      clientId: "${GITHUB_CLIENT_ID}"
      clientSecret: "${GITHUB_CLIENT_SECRET}"
    magicLink:
      enabled: true          # passwordless — requires email config (see dune-email skill)
```

**There is no `providers.localUsers` config, at any userStore tier.** It doesn't exist anywhere in `auth.providers`' real type (`src/config/site-config.ts`) or anywhere else in source. Every account today is created through an OAuth callback or a magic-link request the user initiates themselves — there is no admin-driven "pre-create an account, user activates via magic link" path. See the roadmap note in Gotchas — this would be a reasonable feature to actually build, it just doesn't exist yet.

### Routes generated by mode 1

```
GET  /auth/login                → default login page (theme's templates/auth/login.tsx if present, else a minimal built-in page)
GET  /auth/logout                → destroy session, redirect to /   (GET, not POST)
GET  /auth/me                    → current SiteUser as JSON, or 401 if not logged in
GET  /auth/{provider}             → begin OAuth flow (github, google, discord — only configured ones; others 404)
GET  /auth/{provider}/callback    → complete OAuth, upsert SiteUser, set session cookie, redirect
POST /auth/magic/send             → send magic link email          (NOT /auth/magic-link/send)
GET  /auth/magic                  → verify magic link token, create session   (NOT /auth/magic-link/verify)
```

Session cookie name is `dune_auth` (`SITE_COOKIE_NAME` in `src/auth/middleware.ts`) — HttpOnly, SameSite=Lax, Secure outside `DUNE_ENV=dev`.

## Mode 2: `external-jwt` — validate and trust

Dune validates a JWT on each request, populates `ctx.state.siteUser` from the claims (`provider: "external-jwt"`), and does nothing else. No sessions, no OAuth flow, no user storage.

```yaml
# site.yaml — Clerk example
auth:
  mode: external-jwt
  jwt:
    issuer: "https://your-app.clerk.accounts.dev"
    audience: "your-app"
    jwksUrl: "https://your-app.clerk.accounts.dev/.well-known/jwks.json"
    userIdClaim: sub      # default "sub" — flat fields, not a nested userClaims: {} map
    emailClaim: email     # default "email"
    rolesClaim: roles     # default "roles"
```

There is no `userClaims: { id, email, name }` nested map — `userIdClaim`/`emailClaim`/`rolesClaim` are flat fields on `jwt:`, all optional with the defaults shown, and there is no name-claim option at all (name isn't extracted from the JWT in this mode). `issuer`/`audience` are strongly recommended — without them, any token signed by the same JWKS endpoint is accepted, including tokens minted for a different tenant on a shared IdP.

No routes generated. No sessions. No user records in Dune. Clients pass `Authorization: Bearer {token}`. Optionally, `auth.webhook` (only active with `mode: external-jwt` + `authzStore: local`) registers `POST /auth/webhook` to handle `user.deleted` events and revoke authz tuples — role changes don't need a webhook, they're reconciled per-request from the JWT claims automatically.

## `ctx.state.siteUser` shape

```ts
interface SiteUser {
  id: string;                // UUID (dune mode) or the JWT's userIdClaim value (external-jwt)
  email: string;
  name?: string;
  avatarUrl?: string;
  provider: string;          // "github" | "google" | "discord" | "magic" | "external-jwt"
  providerId?: string;       // the OAuth provider's own user ID
  roles: string[];           // always an array, never undefined
  createdAt: number;         // ms timestamp — a number, not a Date
  lastSeenAt: number;
  enabled: boolean;
  stripeCustomerId?: string; // set after a successful Stripe checkout, if payments are used
}

// ctx.state.siteUser is null on unauthenticated requests — never undefined
```

(`src/auth/types.ts`.) In `external-jwt` mode, `roles` comes from the JWT's `rolesClaim` on every request — there's no persistent record. In `dune` mode, `roles` is a field stored directly on the `SiteUser` record.

### Reading it outside a Fresh handler

Generated CRUD route handlers (from `dune codegen`) and other code that only has a raw `Request` (not a Fresh context) can't read `ctx.state` directly. The auth middleware also serializes the resolved user into an internal `x-dune-site-user` request header (JSON, stripped at the edge — never externally settable) for exactly this case: `requireAuth(req, mode)` from `@dune/core/auth/api-guard` reads it. **Hand-written TSX content pages have no automatic `page.siteUser` prop** — if you need the user there, read the header yourself the same way `api-guard.ts` does.

## Protecting routes

### Redirect unauthenticated users

```ts
// routes/_middleware.ts  (or any nested _middleware.ts)
import type { FreshContext } from "fresh";

export async function handler(req: Request, ctx: FreshContext) {
  if (!ctx.state.siteUser) {
    return Response.redirect(new URL("/auth/login", req.url));
  }
  return ctx.next();
}
```

`ctx.state.siteUser` is populated globally on every request by `mountDuneAuth()`'s middleware (once you've actually called it — see the top of this file) — no opt-in required to get the value. The middleware above only adds the redirect gate.

### Require a specific role

**There is no `ctx.state.authz` and no conventional `@/auth/authz.ts` export.** `mountDuneAuth(app, ctx)` returns `{ resolveUser, authz }` at the call site — Dune doesn't inject `authz` into request state, so a route's `_middleware.ts` has no built-in way to reach it. If you need it there, stash it yourself when you call `mountDuneAuth()`:

```ts
// main.ts (or wherever mountDuneAuth() is called)
export const authCtx = await mountDuneAuth(app, ctx); // authCtx.authz, authCtx.resolveUser
```

```ts
// routes/_middleware.ts
import type { FreshContext } from "fresh";
import { authCtx } from "../main.ts"; // however you exposed it

export async function handler(req: Request, ctx: FreshContext) {
  if (!ctx.state.siteUser) {
    return Response.redirect(new URL("/auth/login", req.url));
  }
  if (!authCtx.authz) return new Response(null, { status: 403 }); // null in external-jwt mode
  const allowed = await authCtx.authz.check({
    who: { type: "user", id: ctx.state.siteUser.id },
    canThey: "access",
    onWhat: { type: "group", id: "member" },
  });
  if (!allowed) return new Response(null, { status: 403 });
  return ctx.next();
}
```

`authz` is `null` in `external-jwt` mode — check `ctx.state.siteUser.roles` (from the JWT) directly instead; there's no polizy authz system to call there.

For content gating via frontmatter `roles:`, this check runs automatically in the page middleware — no manual wiring needed. See **dune-authz** skill.

## `userStore` tiers (mode: dune only)

| Value | User records | When to use |
|-------|-------------|-------------|
| `session` | None — synthesized from OAuth/magic-link claims, stored in the session record itself | OAuth-only. Roles granted after login (e.g. via payment) aren't reflected until the next login. |
| `local` | JSON files at `data/site-users/{id}.json` + `data/site-users/by-email/` index (default) | No DB required. |
| `db` | `site_users` table via Dune's own `DbAdapter` | Requires a database configured — `DUNE_DB_URL`, or `DUNE_DB_PATH` for SQLite (default `data/dune.db`). Dune manages this table's schema itself; you don't define it. Use at scale or for multi-process deployments where flat-file contention matters. |

## Gotchas

**No passwords, and no admin-provisioned local users.** Password auth is out of scope. There's also no `providers.localUsers` — every account originates from an OAuth callback or a magic-link request the user initiates themselves. Don't design a flow around an admin pre-creating accounts; it isn't supported today (flagged as a reasonable feature gap in the roadmap backlog).

**`ctx.state.siteUser`, not `ctx.state.user`.** This is the single most common way to break every example in this file — the field is `siteUser`.

**`ctx.state.siteUser` is `null`, not `undefined`.**

**`auth:` config does nothing by itself, and there's currently no supported way to make it do anything.** `mountDuneAuth()` has no public export from `@dune/core` today — see the top of this file. Don't waste time debugging a broken OAuth flow before confirming this system is even reachable in your installed version.

**There is no session-signing secret to configure.** No `SESSION_SECRET`, no `session.secret` YAML key — sessions are opaque IDs looked up server-side, not self-contained signed cookies.

**`external-jwt` eliminates user storage entirely.** `ctx.state.siteUser.roles` comes from the JWT's `rolesClaim` on every request, not from authz tuples — `authz` is `null` in this mode.

**Magic link routes are `/auth/magic/send` and `/auth/magic`** — not `/auth/magic-link/send`/`/auth/magic-link/verify`. `POST /auth/magic/send` has a fixed-window rate limit owned by Dune (`src/auth/routes.ts`); if you build a custom magic-link flow that calls it directly (or bypasses it entirely), you own your own rate limiting.

**`/auth/logout` is `GET`, not `POST`.** A plain link/redirect works.

**TSX content pages don't get `page.siteUser` for free.** Read the `x-dune-site-user` header yourself if you need the user in a hand-written TSX page — see "Reading it outside a Fresh handler" above.
